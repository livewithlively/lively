# 코드 작업은 워크트리에서 — lively_local_repo_worktree 셀프서비스

**규칙:** 어느 실행 환경(중앙 박스·구성원 로컬 PC·워커 노드)에서든 코드를 만져야 하면 **현재 작업 디렉터리(cwd)에 워크트리를 먼저 떠서 그 위에서** 작업한다. 공유 base 레포(호스트별 클론 — 여러 워크트리의 부모)는 pristine 원본이라 **직접 작업·커밋·빌드 금지**. base 는 물리적으로 읽기전용이 아니므로(구성원이 fetch·최신화는 해야 하니) 이 규율이 작업면 격리의 담보다.

## 세션은 코드 없이 뜬다 — 그게 정상이다
프로젝트 세션은 **맨 프로젝트 폴더**(AGENTS.md·CLAUDE.md·.lively 만)에서 뜬다. **세션 생성은 워크트리를 만들지 않는다.** 코드가 필요해진 시점에 아래 툴로 뜨는 게 규정 동선이다 — 공유 base 를 `ls` 로 더듬지 마라.

프로젝트에 **레포가 연결돼 있지 않아도 마찬가지다** — `lively_local_repo_list` 로 그 머신의 후보를 보고 고른다(둘 이상이라 애매하면 사용자에게 확인). 레포를 연결해 두지 않았을 뿐 코드가 필요한 경우가 많다. 프로젝트 폴더의 `AGENTS.md` '코드 작업' 섹션이 같은 지시를 준다(레포 연결 여부와 무관하게 항상 뜬다).

미리 받아두고 싶으면 웹 **세션 생성 모달의 '레포 준비'**를 쓴다. 그 결과 경로는 `.lively/project.json` 의 `provisioned` 에 기록되지만 **참고일 뿐 1순위가 아니다** — 그 준비를 한 프로젝트에만 있고, 워크트리가 회수되면 항목이 지워진다. 툴이 이미 뜬 워크트리를 그대로 재사용하므로 그냥 툴을 부르면 된다.

## 어떻게 (lively 로컬 MCP — 환경 무관 동일)
- `lively_local_repo_list` — 이 머신에서 워크트리를 뜰 수 있는 등록 레포 + 로컬 base 상태(clone 여부·현재 브랜치·원격 대비 최신).
- `lively_local_repo_worktree {repo, path?, branch?, ref?}` — base 를 확보(로컬에 없으면 clone·있으면 fetch)한 뒤 **cwd(기본) 또는 지정 경로에 격리 브랜치 워크트리**를 만든다. base 워킹트리는 건드리지 않고 원격 최신(origin/<ref>)에서 분기한다. 프로젝트 세션이면 브랜치 기본값은 그 프로젝트 브랜치이고, 아니면 `wt/<repo>`. → **반환된 워크트리 경로에서** 편집·커밋·빌드하라.
- `lively_local_repo_worktree_remove {repo, path?, force?}` — 워크트리 제거(base·다른 워크트리 무영향).
- lively 가 그 머신의 base 위치·격리를 알아서 해석하므로 하네스는 실행 환경을 몰라도 된다.

## private 레포에서 클론이 막히면 — 길은 주소의 종류와 자리에 따라 다르다
private 레포에서 `could not read Username`·`Authentication failed`·`Permission denied (publickey)` 가 나면 자격이 없거나 거절된 것이고, `Host key verification failed` 면 그 컴퓨터가 git 호스트의 ssh 호스트키를 아직 모르는 것이다. 실패 메시지가 그 자리에 맞는 길을 함께 알려 준다. 원격에 닿는 git 은 사람에게 묻지 않고 돈다 — 자격이 없으면 멈추지 않고 곧바로 실패한다.

**https 주소로 등록된 레포는 라이블리에 등록한 내 HTTPS 토큰으로 받는다 — 박스에서도 내 PC 에서도.** `me_git_credential_set {kind:"https", host:"<git 호스트>", token:"<개인 액세스 토큰>"}` 로 등록한다(웹은 [내 설정 ▸ 레포 접근 ▸ git 인증 관리]). 박스에서는 게이트웨이가 그 토큰을 홈에 내려 두고, 내 PC(노트북·데스크톱)에서는 워크트리 툴이 git 을 띄울 때 게이트웨이에서 받아 그 git 한 번에만 쓴다. 그래서 내 PC 에 git 자격을 따로 설정하지 않아도 된다. 받아 온 토큰은 파일·키체인에 남기지 않는다. 내 PC 로 내려오는 것은 **본인이 등록한 HTTPS 토큰뿐**이다 — 조직(게이트웨이) 자격과 SSH 개인키는 내려오지 않는다. 등록한 토큰이 없거나 거절되면 그 컴퓨터의 git 자격(credential helper)으로 한 번 더 시도한다.

**ssh 주소로 등록된 레포 + 라이블리 박스(웹 터미널·격리 세션)는 `me_git_credential_set {kind:"ssh", host:"<git 호스트>"}` 로 등록한다.** 박스가 키페어를 만들어 개인키는 암호화해 DB에 두고 **공개키만 돌려준다**. 그 공개키를 해당 호스트(GitHub·GitLab) 계정에 등록하면 끝이고, 등록 즉시 홈에 반영되어 **열려 있는 세션에서도 바로** 쓰인다(세션 재접속 불요). 박스에서는 셸에서 `ssh-keygen` 으로 홈에 키를 직접 만들지 않는다. 당장은 되지만 그 키는 라이블리가 모른다 — 관리탭에 안 보이고, 오프보딩 때 회수되지 않고, 홈이 재생성되면 유실되며, 나중에 정규 등록을 하는 순간 `IdentitiesOnly` 때문에 조용히 무시된다. 한 호스트에는 자격을 하나만 둔다 — 같은 호스트에 HTTPS 토큰을 등록하면 SSH 키 등록이 그 토큰으로 바뀐다.

**ssh 주소로 등록된 레포 + 내 PC 는 그 컴퓨터의 ssh 키를 쓴다.** 라이블리에 등록한 SSH 개인키는 박스 밖으로 나오지 않으므로 `me_git_credential_set {kind:"ssh"}` 로 등록해도 내 PC 의 클론은 풀리지 않는다. 내 PC 에서는 `ssh-keygen -t ed25519` 로 키를 만들고(이미 있으면 생략) 공개키(`~/.ssh/id_ed25519.pub`)를 git 호스트 계정의 SSH 키에 등록한 뒤, 터미널에서 `ssh -T git@<git 호스트>` 를 한 번 실행해 호스트키 지문을 확인하고 받아 둔다. `lively doctor` 가 등록 레포의 git 호스트마다 이 접속을 시험해 호스트키 미등록·키 거부를 미리 알려 준다.

**받아 둔 레포를 갱신하지 못하면 결과에 `fetch_warning` 이 온다.** 워크트리·핀은 그때 «마지막으로 받아 둔 origin» 기준이라 최신이 아닐 수 있다 — 그 SHA 를 최신이라고 말하지 않는다.
- **발견성:** 위 `_list`·`_worktree` **두 개만** 스키마가 항상 세션에 실린다 — MCP 서버가 `_meta["anthropic/alwaysLoad"]` 를 선언한다(코드 작업의 진입점이라 발견을 운에 맡기지 않는다). 나머지 로컬 툴(핀 계열 등)은 하네스의 tool search 대상이라 **이름만** 실리고 스키마는 쓸 때 로드된다 — "모든 툴 스키마가 자동 주입된다"고 전제하지 마라.

## 왜 base 직접작업을 피하나
- base 는 여러 프로젝트 워크트리의 **부모**라 오염이 전파되고, **다른 사람이 진행 중인 작업**이 체크아웃돼 있을 수 있다(절대 날리지 말 것).
- base 는 주기 갱신과 워크트리 생성 시 fetch 로 최신을 유지하므로, base 에서 직접 당길 이유가 없다.
