# Lively

**IT Product 조직을 위한 AX 솔루션**

라이블리는 AI에 의해 **자동으로 축적되고 관리되는, 정규화된 업무 맥락 저장소**입니다.
구성원의 AI에게 필요한 맥락을 적절히 주입하여, 모두가 업무에 **최상의 AI 성능을 편차 없이** 활용할 수 있게 합니다.

## 문제

### AI는 세상 모든 것을 알지만, 우리 회사는 모릅니다

모델은 이미 충분히 똑똑합니다. 그런데 우리 회사의 제품과 코드, 결정과 진행 상황은 세상 어디에도 학습돼 있지 않습니다. 성과를 가르는 것은 AI의 지능이 아니라, **AI가 우리 회사를 아느냐**입니다.

1. **모델로는 이제 격차가 나지 않습니다.** 경쟁사도 우리와 같은 챗GPT와 클로드를 씁니다. 모델의 성능은 이미 상향 평준화됐습니다.
2. **격차는 AI에게 주는 맥락에서 납니다.** 같은 모델이라도 우리 제품과 코드, 결정을 알고 일하는 순간, AI는 범용 도구가 아니라 우리 회사의 전력이 됩니다.
3. **그 맥락이 지금은 방치돼 있습니다.** 메신저와 문서, 코드와 회의에 흩어져 있고, 개인 대화창에서 생겼다 사라집니다. 모으는 사람도, 관리하는 주체도 없습니다.

> **모델은 사도 되지만, 맥락은 살 수 없습니다.**
> 우리 회사의 맥락은 우리 안에만 있고, 모아서 AI에게 주는 회사만 그 격차를 가집니다.

### 회사의 기억은 지금, 아무도 관리하지 않습니다

검색이 안 되는 게 아닙니다. 찾아도 무엇이 맞는지 모르고, 정리해도 금방 낡고, 오늘 한 일이 내일 남지 않습니다.

| | 무슨 일이 일어나는가 |
|---|---|
| **찾아는 주는데, 뭐가 맞는지 모릅니다** | 2년 전 문서와 지난주에 바뀐 결정이 나란히 검색됩니다. AI는 그중 옛 문서를 읽고, 자신 있게 틀린 답을 합니다. |
| **정리해 둬도, 금방 낡습니다** | 그래서 위키를 만듭니다. 하지만 회사 일은 매일 바뀌고, 정리는 누구의 업무도 아닙니다. 위키는 만든 날부터 낡기 시작합니다. |
| **오늘 AI와 한 일이, 내일이면 사라집니다** | 팀원 A가 오늘 AI와 결론을 냈어도, 내일 팀원 B의 AI는 아무것도 모릅니다. 대화가 끝나면 조직에는 아무것도 남지 않습니다. |

셋의 공통 원인은 하나, **회사의 기억을 관리하는 주체가 없다는 것**입니다.
라이블리는 이 관리를 사람이 아닌 AI에게 맡깁니다.

## Lively는 무엇인가

### 1. AI에 의해 자동으로 쌓이고 관리되는 업무 맥락 저장소

메신저·이메일, 문서·이슈, 코드와 결정, AI 작업 결과물까지 하나의 저장소에 자동으로 모이고, 정리되어, 필요한 순간 AI에게 주입됩니다. 구성원이 할 일은 하나입니다. **라이블리를 열고, 클로드에게 물어보면 끝입니다.**

```
흩어진 원천                      Lively                        모든 구성원의 AI 세션
메신저 · 이메일
문서 · 드라이브    ─ 자동수집 ─▶  업무 맥락 저장소  ─ 필요한 맥락만 주입 ─▶   Claude / Codex / …
코드 · 커밋                    (증류 · 분류 · 연결)
결정 · 회의록                        ▲
이슈 · 태스크                        └────── 세션의 산출물이 다시 회사의 지식으로
```

- **자동 수집·저장** — *증류*(대화는 버리고 사실과 결정만 남김) · *분류*(회사 분류체계의 제자리에 저장) · *연결·임베딩*(관계를 잇고 의미를 수치화)
- **자동 축적·관리** — *스스로 생성*(AI가 필요하면 프로젝트·지식을 만듦) · *연결·최신화*(새 지식은 연결되고 낡은 지식은 갱신) · *중복 방지·검토*(중복은 걸러지고 사람이 검토)
- **필요한 맥락만 주입** — *주입 수준 설정*(중요한 지식만 본문까지) · *키워드·의미 검색*(AI가 스스로 찾아 읽음) · *자동 주입*(질문이나 코드와 관련된 지식이 자동으로)

### 2. 세팅 실력과 관계없이, 모두가 같은 도구를 이어받은 AI 세션의 표준화

**한 사람의 세팅이, 조직의 표준이 됩니다.** AI에 능숙한 구성원이 만든 커스텀 스킬·훅·MCP 연동은 Lively에 올려 전 구성원이 바로 쓰도록 승격됩니다. 바닥은 올라가고, 모두의 개선이 쌓여 천장도 계속 높아집니다.

개발 직군이 본인이 쓰려고 만들어 둔 도구가, 기획자의 AI에도 자동으로 장착됩니다. 백엔드 리드가 만든 릴리스 점검 스킬, 데이터 엔지니어가 붙인 read-replica 연동, 플랫폼 개발자의 사내 검색 MCP — 누가 세션을 열든 그 도구가 함께 옵니다.

| 출발점 | 개인 세팅으로 도달 | Lively가 채우는 맥락 |
|---|---|---|
| 기획자 (Claude 앱/웹) | 30 | +70 |
| 개발자 (Claude Code) | 70 | +30 |
| 개발책임자 (Claude Code + Skills) | 90 | +10 |

출발점이 어디든, 라이블리가 나머지를 채웁니다.

### 3. 수준 높은 맥락을 쌓는 Lively만의 방법

라이블리는 회사 맥락을 **프로젝트**와 **지식**으로 구분해 분류체계에 따라 저장합니다. 프로젝트와 프로젝트, 프로젝트와 지식, 지식과 지식이 연결지어 쌓이고, 이 구조를 라이블리의 프로젝트 관리 화면에서 직접 보고 관리합니다.

프로젝트는 **필요 지식**을 요구하고 **산출 지식**을 만듭니다. 후속 프로젝트로 이어지고, 지식끼리도 연결됩니다. 모든 프로젝트·지식은 분류체계의 제자리에, 연결과 함께 저장됩니다.

별도 PM 툴 없이도, 프로젝트·태스크와 연결된 지식을 라이블리에서 바로 관리합니다.

### 4. 기존 AI 모델들에 의존하지 않는, 아예 별개의 맥락 관리층

팀마다, 심지어 같은 팀에서도 사람마다 쓰는 모델이 다릅니다. 라이블리는 **AI 위의 독립된 층**에서 회사 맥락을 관리하므로, **특정 AI 모델에 종속될 필요 없이** 지금 상태를 유지할 수도, 언제든 갈아끼울 수도 있습니다.

```
        Lively — 회사 맥락 관리 층
                  ⇅  언제든 교체
   Claude   Gemini   ChatGPT   그 외
   모델은 갈아끼우고, 맥락은 이 층에 남습니다
```

- **지금 구성 그대로** — 도구를 바꾸라고 하지 않습니다. 팀이 쓰던 AI에 라이블리를 연결만 하면 그날부터 같은 회사 맥락으로 일합니다. *(도구 교체 0 · 재교육 0)*
- **최적 조합을 계속** — 모델 성능과 요금은 몇 달 만에 뒤집힙니다. 팀·사람 단위로 갈아끼우며 그때의 최적 조합을 유지합니다. *(교체할 때 맥락 이전 작업 0)*
- **장애에도 안 멈춤** — 한 벤더에 장애나 정책 변경이 생겨도, 다른 AI로 옮겨 같은 맥락 그대로 업무를 이어갑니다. *(차선 AI 즉시 전환)*
- **락인 없는 저장소** — 회사의 맥락이 AI 회사 계정에 갇히지 않습니다. 매니지드든 셀프호스트든 **저장소의 주인은 귀사**입니다. *(벤더 종료·가격 인상에도 자산은 우리 것)*

### 5. 운영은 맡기는 매니지드, 데이터는 소유하는 셀프호스트

| | **매니지드** (운영 편의) | **셀프호스트** (데이터 주권) |
|---|---|---|
| 어디에 | Lively 클라우드의 귀사 워크스페이스 | 귀사 인프라 · 사내망 경계 |
| 설치·운영·업데이트 | 저희가 맡습니다. 준비물 없이 가장 빠르게 시작 | 귀사 경계 안에 통째로 설치 |
| 데이터 | 귀사 구성원만 접근, 모든 접근이 기록됩니다 | 회사 기억의 원본이 경계 안에만 존재 |
| 외부 전송 | — | 정책 게이트가 허용한 조각만 나갑니다. 저장소를 통째로 보내는 일은 없습니다 |
| 폐쇄망 | — | 로컬 모델을 연동하면 외부 트래픽 0인 완전 폐쇄망 구성도 가능 |
| 권장 | 일반 조직의 기본값 | 보안 · 규제 조직 |

보안 요건이 커지면 매니지드에서 셀프호스트로 전환할 수 있습니다.
**AI 도구를 바꿔도 지식은 그대로** — 저장소가 특정 벤더에 묶이지 않는 구조라, 하네스를 갈아끼워도 조직의 지식은 이식됩니다.

## 왜 Lively인가

### 도입 4주, 구성원들의 말

한 AI 기업의 제품 조직에 라이블리를 도입했습니다. 아래는 4주 차 구성원 설문 결과와 실제로 일어난 일들입니다.

> "검토해 본 적 없는 도메인도, 팀원들이 증류해 둔 지식을 참고하게 하면 좋은 답변까지의 시행착오가 줄었습니다."
> — 로컬 Claude Code에서는 `CLAUDE.md`를 관리해도 처음 보는 도메인은 매번 프롬프트로 설명해야 했다는 응답

> "개발팀을 통해 쿼리를 작성할 필요 없이, 자연어로 지시할 수 있어 편했습니다. 최근 1주는 개발 요구사항 작성도 대부분 라이블리로 옮겼습니다."
> — 전환율 퍼널 데이터를 AI 세션에서 직접 뽑은 PO의 응답

> "기존 클로드 코드로 작업하던 것 이상의 효율과 속도였고, 실제 과업에서 임팩트가 났기에 추천할 수 있습니다."
> — 로컬 Claude Code를 능숙하게 쓰던 PO가 추천 의향 9점과 함께 남긴 이유

**Case 1 — PO도 몰랐던 심사 기준을, AI가 먼저 제안**
심사 기능 개편을 기획할 때, 유관 부서와 논의해 변경돼 있던 기준 맥락이 자동으로 주입됐고, AI가 이 기준을 기획에 반영해야 한다고 먼저 제안했습니다. PO가 인지하지 못했던 맥락까지 반영되어 프로젝트가 성공적으로 마무리됐습니다.

**Case 2 — 타 부서 의뢰, 접수부터 결론까지 당일 종결**
담당 개발자가 회사에 없던 데이터 영역의 이상치 의뢰를, AI가 원본 6,096건 실측과 코드 확인으로 3중 검증해 당일 결론을 냈습니다.

> "우리 회사의 맥락과 데이터를 활용해, 전 구성원이 AI를 효율적으로 활용하게 해주는 솔루션"
> — 설문에서 PO가 남긴 라이블리 한 줄 정의

### AI 교육·컨설팅·SaaS가 아닌, 라이블리를 선택해야 하는 이유

| | 잘하는 것 | 그래도 남는 것 |
|---|---|---|
| **일반적인 AI 교육** | 도구 사용법과 프롬프트 기법. 개인의 숙련도는 분명히 올라갑니다 | 교육이 끝나면 각자의 습관으로 돌아가고, 조직의 프로세스와 맥락 단절은 그대로 남습니다 |
| **범용 AX 컨설팅** | 진단부터 구현까지. 잘 만난 파트너는 실제로 시스템을 만들어 주기도 합니다 | 남는 것은 그 시점의 맞춤 구축물입니다. 컨설턴트가 떠난 뒤의 운영과 개선은 다시 조직 몫이고, 제품처럼 계속 업데이트되지 않습니다 |
| **범용 AI 협업툴** | 각 도구 안의 검색과 요약은 이미 훌륭합니다 | 맥락이 각 도구 안에 갇혀 있고, 찾은 결과가 조직의 지식으로 축적되지 않습니다 |

**Lively는 다릅니다.**

- **판정을 거쳐 축적되는 조직 지식** — AI가 만든 지식도 중복 확인·검토·최신화를 거쳐 쌓입니다. 쓸수록 오염되는 게 아니라, 쓸수록 정확해집니다.
- **AI의 작업까지 프로젝트로 귀속** — 누가, 어느 AI가, 어떤 프로젝트에서 무엇을 산출했는지 자동으로 기록됩니다. 조직이 AI의 일을 관리할 수 있게 됩니다.
- **셀프호스트까지 완제품** — 주권이 필요하면 통째로 귀사 인프라에 설치합니다. 부품을 조립하는 것이 아니라, 완성된 제품을 설치하는 것입니다.
- **하네스 중립** — Claude Code든 Codex든 같은 맥락이 주입됩니다. AI 도구를 갈아타도 조직의 지식은 그대로 남습니다.

### 이미 검토하셨을 조합들에도, 같은 자리가 비어 있습니다

| 조합 | 잘하는 것 | 그래도 남는 공백 |
|---|---|---|
| **AI 구독 올인원** | 추가 벤더 없이 구독 하나로 검색·메모리·정책 관리까지. 가장 싸고 빠른 시작 | 메모리는 개인·레포 단위의 평평한 파일이고, 검색은 매번 원본을 다시 뒤질 뿐 축적되지 않습니다. 프로젝트 축과 셀프호스트가 없습니다 |
| **AI 하네스 + 문서 SaaS** | 협업 편집 UX는 최고 수준이고, 구독 하나로 여러 소스 검색까지 됩니다 | AI가 만든 페이지가 검토·중복 정리 없이 그대로 쌓입니다. 잘 쓸수록 검색이 오염되고, 코드·DB와 데이터 주권은 그 밖입니다 |
| **AI 하네스 + 엔터프라이즈 검색** | 100+ 커넥터와 문서 권한을 인식하는 검색. 대기업 검색 축의 정답 | 읽기 전용 인덱스라 AI 산출물이 쌓일 집이 없습니다. 최소 좌석 수와 연 수만 달러부터라 중견 이하 조직에는 과합니다 |
| **직접 조립** (메모리 SDK · OSS 스택) | 주권과 부품 선택의 자유는 최고 수준이고, 라이선스 비용도 0 | 검색·메모리·프로젝트가 서로 모르는 3~5개 시스템입니다. 통합·운영·UI를 조직이 6~12개월 직접 만들고, 계속 유지해야 합니다 |

라이블리는 이 자리를 완제품으로 채웁니다. 지금 쓰는 하네스와 도구는 그대로 둔 채, 그 위에 얹습니다.

### "우리는 개발팀이 직접 만들고 있어요"

훌륭한 시작입니다. 앞서가는 조직일수록 개발팀이 먼저 움직입니다. 다만 그 길은 **구조적으로** 세 가지 한계에 부딪힙니다.

1. **만드는 사람 ≠ 쓰는 사람** — 개발자는 스킬을 만들어 올리고 MCP로 사내 도구를 연동해 둡니다. 하지만 터미널·설정 파일의 문법 앞에서, **화면(UI)이 필요한 PM·PO·기획자**는 결국 밖에 남습니다. 쓰지 못한 사람들은 다시 브라우저 챗으로 돌아갑니다.
2. **가장 바쁜 사람들의 '다음에'** — 회사 전체를 아우르는 전방위 작업은 언제나 **하드 데드라인이 있는 로드맵 과업**에 밀립니다. 스프린트마다 순위가 내려가고, 절반쯤 만들어진 채 멈추는 경우가 대부분입니다.
3. **한 회사용 시스템의 비효율** — 이걸 만들 수 있는 개발자는 조직에서 **가장 비싼 인력**입니다. 그 시간을 한 회사에서만 쓸 시스템에 붓는 것보다, 여러 조직이 개발·유지보수 비용을 나누는 공용 시스템을 쓰는 쪽이 효율적입니다.

개발팀의 시간은 **귀사의 제품**에 쓰여야 합니다. 맥락 인프라는 이미 만들어져 있습니다.

## 이런 조직이라면, 라이블리가 맞습니다

- **기획 × 개발의 협업 구조를 고치고 싶은 팀** — 스펙 재확인 왕복, 결정 유실, 뒤늦은 재작업. 기획팀과 개발팀 사이의 보이지 않는 비용을 줄이려는 기업.
- **AI는 쓰는데, 조직 차원의 효과가 아쉬운 팀** — AI 도구를 이미 쓰고 있지만, 성과가 잘 쓰는 몇 사람의 개인기에 머무는 조직.
- **업무 맥락이 여러 도구에 흩어져 있는 조직** — 결정은 메신저에, 스펙은 문서에, 태스크는 이슈트래커에 흩어져 있고, 전체 그림을 한곳에서 보는 사람이 없는 조직.
- **AI 전환을 실사용으로 검증하고 싶은 CPO·CTO** — 보고서와 데모가 아니라, 진행 중인 실제 프로젝트에서 효과를 확인한 뒤 결정하려는 리더.

## 도입 절차

귀사에서 준비하실 것은 두 가지뿐입니다.

1. **제품팀 구성원의 Claude Code(또는 Codex) 플랜** — 라이블리는 AI를 되파는 서비스가 아니라, 귀사의 AI가 회사를 알게 만드는 플랫폼입니다. 실행 주체는 귀사 명의의 플랜·API 키로 지원해 주세요. 이미 쓰고 계시다면 추가 준비는 없습니다.
2. **업무 도구·코드·DB의 읽기 연결 권한** — AI가 회사를 알려면 그 기억이 있는 곳에 **'읽기'로만** 닿으면 됩니다. 수집 범위와 권한 정책은 사전에 함께 확정하며, 합의되지 않은 채널은 연결하지 않습니다.

## 직접 설치하기 (셀프호스트)

Node.js 20+ 와 PostgreSQL이 필요합니다.

```bash
git clone https://github.com/livewithlively/lively.git
cd lively
cp .env.example .env      # 토큰·데이터베이스 URL 설정
npm ci
npm run build
npm start
curl localhost:8080/healthz
```

MCP 클라이언트를 `http://localhost:8080/mcp` 로 연결하고 `AUTH_TOKENS_JSON` 의 bearer 토큰을 씁니다.
전용 서버용 Docker Compose와 설치 스크립트는 [`deploy/`](deploy/) 에 있습니다.

- [`docs/architecture.ko.md`](docs/architecture.ko.md) — 아키텍처·코드 관례·서브시스템 지도
- [`deploy/README.md`](deploy/README.md) — 서버 설치
- [`kit/README.md`](kit/README.md) — 멤버 키트(CLI·하네스 어댑터·훅)

## 라이센스

디렉터리에 따라 세 가지 라이센스가 적용됩니다.

| 경로 | 라이센스 |
|---|---|
| `kit/` | Apache-2.0 |
| `src/ee/` | Lively Enterprise License (프로덕션 사용에 구독 필요) |
| 그 외 전부 | AGPL-3.0-only |

`src/ee/` 는 **선택 사항**입니다. 코어가 이를 정적으로 import 하지 않으므로, `src/ee/` 를 지워도 빌드되고 구동됩니다. SQL 방화벽·테이블 정책·시크릿 마스킹·채널 가드 같은 **기본 안전장치는 코어(AGPL)** 에 있습니다 — 무료판이 위험한 쪽이어서는 안 되기 때문입니다.

`kit/` 은 영원히 Apache-2.0으로 두고, 코어를 SSPL·BUSL로 조이지 않으며, 지금 AGPL인 기능을 `src/ee/` 로 옮기지 않겠다는 약속을 공개했습니다 — **[LICENSING.md](LICENSING.md)**.

이름은 라이센스가 아니라 상표 정책을 따릅니다: [TRADEMARK.md](TRADEMARK.md). 포크는 자유이고, 이름만 바꿔 주세요.
